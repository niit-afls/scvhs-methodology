# The Decision Log

> A construct-by-construct record of the VALIDATE and HARDEN phases.  
> Produced in real time. Committed alongside the artifact. The evidence of comprehension and ownership.

---

## What the Decision Log Is

The Decision Log is a single file, filled during VALIDATE, completed during HARDEN, and committed with the artifact at SHIP. It is the engineer's documentation of what they reviewed, what they found, and what they did about it — construct by construct, not as a summary after the fact.

### The Decision Log is NOT:
- **A code comment.** Comments live in the code file. The Decision Log lives in a separate `.md` file. Code comments say what the code does; the Decision Log says what the AI did that needed changing and why.
- **A test file.** Tests verify behavior automatically. The Decision Log records human evaluation, which captures defects that tests cannot catch: wrong semantic element choices, AI-fabricated values, missing constraints, comprehension gaps.
- **A code review document.** Code reviews are team-facing and advisory. The Decision Log is the individual learner's record of their own validation process, construct by construct.
- **An after-the-fact summary.** "I reviewed the AI output and found 3 issues" is not a Decision Log. The Decision Log is filled one entry at a time, in real time, as each construct is read.

### The Decision Log IS:
- The evidence that the learner validated the AI output (not just ran it and trusted it)
- An AI-proof assessment artifact, it cannot be generated by an AI tool because it requires the learner to document what they found against their own spec, construct by construct
- An ownership record — in a production context, it answers "did you review this before shipping?"
- A pattern-recognition tool — across sprints, the learner's logs reveal recurring AI failure modes for specific technologies

## Structure

### File header (filled once per sprint)

```
Learner:
Sprint: [Number], [Title]
Date:
Spec file referenced:
AI-generated files reviewed:
```

The file itself is named `AI_Decision_Log_S[NN]_v1.md`; there is no separate "Version" field, the filename carries the version (see Filing Convention, below).

### Entry format (one entry per Constraint, one entry per Acceptance Criterion)

Entries are anchored to the spec, not to the artifact's code structure. One entry per
Constraint and one entry per Acceptance Criterion in the spec, its title copied word for
word, not summarized or paraphrased. Constraint entries first, then Acceptance Criterion
entries, in the same order the spec lists them. If an entry cannot name which line of the
spec it is checking, it is not a valid entry.

```
Constraint-Entry [N]: [Constraint text, copied word for word from the spec]

What the code does (plain English):
[Describe the actual construct being checked. If you cannot explain it, that is a defect, flag it.]

Match with spec:
Yes / No / Not reviewed

Issue:
[None, or the specific defect. What did the AI do? What does the spec require?]

Check:
[n/a, or how you confirmed it: read the code, ran a specific test, compared against your hand-built reference in Mode 1.]

Fix:
[No change, or the exact change made in the code.]
```

Acceptance Criterion entries use the identical fields, headed `Acceptance-Criterion-Entry [N]:` instead.

"Not reviewed" is a legitimate answer, not a placeholder to avoid. If the AI's actual approach never exercised a code path the spec's item describes (an edge case, a boundary condition), say so rather than guessing pass or fail.

### Summary (filled at the end)

```
Total checked:
Issues found:

Correct:
[List what passed: constructs or decisions where AI output matched spec.]

Main issue:
[List each defect, referencing its entry, e.g. Constraint-Entry 2.]
```

### Reflection (filled at the end)

```
Where did the AI diverge most from your spec — and how did you know it was wrong?
[2–4 sentences.]
```

## Entry Depth Is the Same in Every Mode

Every Constraint and every Acceptance Criterion gets a full entry, in every mode, passing
or failing alike:
- "What the code does": required, specific, even when Match with spec is Yes
- "Match with spec": Yes / No / Not reviewed
- "Issue," "Check," "Fix": filled when Match is No; "None" / "n/a" / "No change" when Yes

**Why "What the code does" is never blank, even for a passing entry:** the explaining IS
the comprehension activity. A learner who writes nothing more than "Yes" for a passing
entry has not completed it. The cognitive work of writing "this method reads the
connection URL from a constant and opens it with `DriverManager.getConnection()`,
matching the spec's requirement to hardcode configuration" is what builds comprehension,
not the observation that it looks correct.

What changes by mode is not entry depth, it is how you determine the answer:

- **Mode 1 (Hand-First + Validate AI):** you compare the AI's version against your own
  hand-built reference, which you already know is correct. "Check" names that comparison.
  If the AI differs, that is the Issue; "Fix" describes what would need to change in the
  AI's version, informational only, since your hand-built version ships and the AI
  version is discarded, never edited.
- **Mode 2 (Hybrid) and Mode 3 (AI-Drafted Spec):** identical to each other. The AI tool
  constructed the artifact; "Check" means validating directly against the spec. Mode 3
  changes who drafted the spec, an AI tool drafts it and the learner reviews and
  finalizes it, but nothing about Construct, Validate, or this Decision Log.

## The Comprehension Defect

If the learner cannot explain what the code does in plain English, they record:

```
What the code does (plain English):
I cannot explain what this code does.

Match with spec:
No

Issue:
Comprehension defect, this construct is not understood.

Check:
Could not write a plain-English explanation after reading the code.

Fix:
[After researching and understanding the construct:]
This code [explanation]. It matches / does not match the spec because [reason].
[If it does not match spec: fix described.]
```

A comprehension defect must be resolved before HARDEN is complete. It cannot be shipped.

## What Specific Looks Like

The standard of a Decision Log entry is **specific and traceable**. Each entry must be specific enough that:
1. A different engineer reading the log can understand exactly what was wrong.
2. The entry can be matched to a specific line in the AI-generated file and a specific criterion in the spec.
3. The pattern of defects across entries reveals something about how this AI tool fails for this technology.

### Comparison: Vague vs Specific

**Vague (not acceptable):**
> The AI made some errors with the semantics.

**Specific (acceptable):**
> Spec required each project wrapped in `<article>` — AI used `<div class="project">`. Div has no semantic value; screen readers cannot identify project entries as independent content. Caught by comparing the AI file line by line against the spec's Projects section. Fixed by replacing each `<div class="project">` with `<article>`.

**Vague (not acceptable):**
> The CSS has some issues with selectors.

**Specific (acceptable):**
> Spec said no `!important`. AI wrote `color: #FFFFFF !important` on `nav a`. This breaks the cascade — any future override will require another `!important`. Caught with Ctrl+F search for `!important` in the stylesheet (found 2 occurrences). Fixed by removing `!important` and raising specificity to `header nav a` — now wins the cascade correctly without forcing.

## The Decision Log Across Multiple Sprints

The Decision Log is per-sprint — a new file for each sprint. But across sprints, the learner's Decision Logs build a portfolio of AI failure pattern knowledge:

- Sprint 1 Decision Log: AI omits lang attribute; AI uses div instead of article; AI generates multiple h1s
- Sprint 2 Decision Log: AI uses !important to resolve conflicts; AI uses px for font-size
- Sprint 3 Decision Log: AI uses desktop-first breakpoints; AI writes arbitrary Tailwind values like w-[437px]

By Sprint 7, the learner has documented enough failure patterns to anticipate what to look for before they read the AI output. This is the meta-skill that SCVHS builds across a course: not just "I can catch AI defects" but "I know in advance where AI will fail for this technology, and I check those places first."

## Filing Convention

Decision Log files follow this naming pattern:

```
AI_Decision_Log_S[NN]_v1.md
```

Examples:
```
AI_Decision_Log_S01_v1.md
AI_Decision_Log_S03_v1.md
AI_Decision_Log_S07_v1.md
```

The file is committed to the repo in the same commit as the corrected artifact. It is not a draft
file, it is committed once, complete.

**Never edit a Decision Log file in place once it has been committed (locked 2026-07-27).** This
applies to every kind of revision, adding a note about a newly discovered defect, correcting an
entry, reclassifying a finding after further testing, anything at all. Editing the existing file
means a correct finding can be silently overwritten by an incorrect one (or the reverse), with no
trace visible anywhere except by manually diffing commit history construct by construct, which
nobody reliably does.

Instead, save a new file: `AI_Decision_Log_S[NN]_v2.md`, then `_v3.md`, and so on. Keep every
version, delete none. At the top of `v2` and later, add one line stating what changed from the
previous version and why, for example: "v2: connection-failure defect from v1 confirmed and
restored after retesting, was incorrectly cleared in a prior edit." The latest version is what
counts for Ship and grading. Earlier versions stay in the repo specifically so a reviewer can see
how a finding evolved, or was lost, directly in the file listing, without needing to go looking for
it in git history.
